Design discussion · a new build on Context Graph

The Governed-Workflow Platform

A real application that demonstrates Context Graph — and, underneath it, the constrained expert system made buildable. It's built in two LLM-driven development stages, both run by experts: Stage 1 defines a domain's building blocks (CG & its ontology, Rules, Flows, States, Integrations, Actions); Stage 2 composes those blocks into real applications — and because the Stage-2 LLM may only wire existing, typed blocks, the usual LLM-dev mistakes become structurally impossible. An integration engine feeds events in; a deterministic runtime executes, with any LLM confined to a defined Action.

A starting point for discussion — opinionated where the substrate already decides it, open where it's ours to choose. Companion to The Constrained Expert System and the Context Graph architecture.

The product

What we're building

A domain-oriented application, built the way this platform makes possible: in two LLM-driven development stages, both run by experts — possibly of different qualifications, but experts, not end-users, in both. This is a development process, start to finish. What makes it new is not that an LLM writes the app; it's what the LLM is allowed to touch at each stage.

  • Stage 1 — define the building blocks & the DSL. A domain architect, with the LLM, defines the concrete blocks for a domain: the ontology (over CG), the rule vocabulary, the flow templates, the state machines, the integration bindings, the action catalog. This stage is bounded by the platform's fixed Concepts (Rules · Flows · States · Integrations · Actions · CG) and their CG implementations — not by application logic. You can only make things that are one of those kinds.
  • Stage 2 — compose blocks into applications. An app builder, also with the LLM, assembles the Stage-1 blocks into real applications. Here the LLM's entire universe is the set of artifacts Stage 1 already defined — so it cannot drift, cannot re-implement, cannot forget to reuse, cannot mis-architect. (The next section makes that guarantee precise.)

That is the constrained-expert-system thesis turned into a piece of software — applied twice, recursively. The essay argued the why; this document proposes the what and asks the questions we need to answer before building. We picked a domain-neutral demonstrator on purpose: the point of the first build is to show the platform, not to sell a vertical. The worked example is a generic governed request workflow — a request arrives, rules decide, a flow routes it through review, a human signs, a decision trace is recorded — and the same machinery re-skins to deals, claims, clinical orders, or investigations later.

◆ The one invariant — restated honestly
Not "no LLM at runtime." The truthful line is: no unbounded LLM at runtime. The orchestration and rule logic execute deterministically; where a domain genuinely needs judgment, an LLM may act — but only as a declared, typed, gated Action (see below), its inputs and outputs bounded by the ontology and its execution recorded as a decision. The model is never on a free hot path; it is a boxed actor or it is absent.

Naming, for this doc: Stage 1 defines blocks in the Studio; Stage 2 composes them into an App (a versioned bundle: ontology + rules + flows + actions + connector bindings + views); the App runs on the Runtime. End-users — the people who later operate a finished App — are not a stage; they appear only at runtime.

The mechanism

The constraint tower — why the Stage-2 LLM can't make the usual mistakes

The same move — constrain the LLM to defined blocks, not raw code — applied at three levels, each one boxing the level below it. An LLM's whole universe, at any level, is the set of artifacts defined above it. That containment is the guarantee.

Spell out the payoff. The failure modes that plague open-ended "LLM builds my app" agents aren't mitigated here by better prompting — they're structurally unreachable, because the thing you'd need freedom to do wrong isn't in the LLM's action space:

Classic LLM-dev failureWhy it can't happen in Stage 2
Semantic driftevery term must resolve to an L1 ontology type; unbound terms are rejected, not invented
Re-implementing an existing featureit can only reference blocks that exist; it has no path to author a new one
Forgetting to reusereuse is the only option — composition of existing blocks is the sole primitive
Wrong engineering / bad architecturearchitecture is decided at L0/L1 and frozen before the app LLM runs
Ungrounded invention (fake APIs/entities)integrations & actions are a closed, typed catalog — nothing outside it is callable
Inconsistent state handlingstates are declared machines with guarded transitions, not ad-hoc flags
◆ The reframe in one line
Stage 1 fixes the alphabet and the words (bounded by the platform's fixed grammar); Stage 2 writes documents (bounded by that alphabet and those words). Two development stages, both expert-driven and LLM-assisted, together producing one domain app — with the LLM's freedom deliberately spent up the tower, not out into open code.
The architecture

The shape — three planes and a loop

Read it left to right as data; top to bottom as trust. External reality enters through the integration engine, is mapped onto ontology terms, and becomes an event. The runtime drives that event through a flow whose gateways call rules and whose steps move state and fire actions — recording a decision trace at each hop. None of that logic is generated on the hot path: it was all authored earlier in the Stage 1 studio and frozen into an App.

Stage 1

The Studio — defining a domain's building blocks

Stage 1 is where a domain architect and the LLM define the blocks the apps will later be built from — bounded by the platform's fixed Concepts, never by open code. The Studio is a visual, reversible wizard: go forward, go back, watch the model take shape, and ground every term as you go. It defines the domain's blocks in dependency order.

  1. Ontology first — the boundary everything else is checked against. The expert describes the domain in natural language; OntologyAuthor.generate() drafts ObjectTypes, Propertys (typed, with PropertyKind + cardinality), and LinkTypes. Nothing downstream may reference a term that isn't here. This is the anti-hallucination wall.
  2. Rules next — bounded by that ontology. RuleAuthor.generate() turns an intent ("discounts over 20% need VP sign-off") into a DSL rule and dry-runs it against sample cases so the author sees behaviour before approving — the same shape as the clinical "test vignettes" in the essay. Every rule carries its supporting_sentences/provenance.
  3. Flows, states, integrations & actions — the composable behaviour. The author lays out BPMN-lite flow templates (entry events, tasks, rule-gateways, terminal states), the StateMachines they rest on, the integration bindings that feed them, and the action catalog — including LLM-agent actions (§ below), each with a typed contract. These are the blocks Stage 2 will wire together.
  4. Approve & register. The human signs; the blocks enter the domain's versioned catalog at a pinned meta-DSL version. That signature is the trust boundary. Stage 2 then composes these approved blocks into an App — and past the boundary, no unbounded model ever runs.
◆ Why this is largely a UX problem, not an AI problem
The generators (OntologyAuthor, RuleAuthor), the typed ontology that validates what they write, the gate, and versioning already exist in Context Graph. Stage 1 is mostly the reversible visual surface over them — a wizard that makes authoring legible and undoable — plus extending the same treatment to flows. The hard, valuable part is interface and bookkeeping, not new model capability.
◆ "Fixed" meta-DSL means versioned, not frozen
An App pins a meta-DSL version. When the platform ships a v2 (a new property kind, a new gateway type), existing Apps must migrate, not break. Skip this and we rebuild the maintenance rot that killed the rule bases the essay buried. Migration policy is an open decision.
The net-new engine

The flow layer — BPMN-lite over primitives we already have

This is the biggest new build, and the design goal is restraint: not a full BPMN 2.0 engine (the essay is a thirty-year warning about that ambition), but the smallest process model that composes the primitives we already ship. A flow is a graph of five node kinds:

Flow nodeIs really…Backed by
Event entrya normalized external event that starts an instanceintegration engine · event bus
Taska step that runs an Action — webhook, compute, or an LLM-agent — and records itActionDefinition / ActionHandler (webhook | agent)
Gatewaya branch that evaluates a rule and routes on the resultRulesEngine.evaluate()
Timera deferred/scheduled transition ("review due in 90d")scheduler net-new
Statea lifecycle node an instance rests inStateMachine / Transition

Concretely, an authored flow is just data — a shape the Studio emits and the runtime walks:

# app: governed-request · flow: intake  (illustrative)
flow intake:
  on_event: request.submitted
  task map:      action="normalize_to_ontology" → next: decide
  gateway decide:  rule="discount_threshold"
                when exceeds → vp_review
                else          → auto
  task vp_review: action="request_signoff" assignee="role:VP" → next: book
  task auto:      action="auto_approve" → next: book
  task book:      action="book_deal" → state: booked
◆ What the engine must add over lifecycle
Today's Lifecycle is a per-object FSM — legal states and guarded transitions. The flow engine adds the orchestration around it: an instance/run with a cursor, gateway evaluation, task dispatch to actions, a timer scheduler, and a persisted run log. States, rules, and actions stay exactly as they are; the engine is the conductor, not a rewrite.

The Action layer — including the LLM as a boxed actor

Actions are a first-class Concept, not a flow detail: a task invokes an ActionDefinition, which runs a handler and records the execution as a decision. Today handlers are none or webhook; we add an agent handler so an LLM can participate in the running application — but only as a defined, contract-bound block:

An LLM-agent Action declares…which makes it…
ontology-typed inputs (drawn from the instance's objects)grounded — it can't see beyond its declared inputs
a fixed output schema (an ontology type or enum)parseable & validated — output that fails the schema is rejected
a pinned role/prompt + guardrailsversioned & reviewable like any other block
a confidence + fallback (route low-confidence to a human task)safe — judgment without silent trust
execution recorded as a decision on the graphaudited — every agent call is in the trace
◆ Honest boundary at an agent node
An agent Action is not output-reproducible — that's the point of using it. Determinism still holds for the orchestration and the rule-gateways around it; trust at the agent node comes from containment (typed contract), validation (schema), and audit (decision trace), plus confidence-routing — not from replay. Use it where the domain needs judgment; keep it off the paths that must be certifiable.
Events in

The integration engine — and where determinism actually begins

External reality is messy; the runtime is strict. The integration engine is the airlock between them. It has three stages, and the essay's sharpest caveat lives in the middle one.

Connectors (ingress) — the webingest/connectors package already defines a pluggable connector base with real implementations; inbound webhooks and pollers are the same shape. Mapping — the essay's "curly-braces problem": binding a real record to the ontology's terms. A deterministic connector-specific map is the happy path (and the only path exercised in the demo); the unstructured tail uses LLM extraction that reuses the LLM-agent Action contract and is validated by ExtractionValidator, with low-confidence results routed to a human review task. Event bus — a durable ingress log + in-process dispatch keyed on the event contract; pluggable to a broker later.

◆ Be honest about the boundary
"Deterministic" is a claim about the rule logic, not the mapping. If the mapping uses an LLM, that step is not reproducible — so it must be logged, versioned, and reviewable, and ideally confidence-scored, with low confidence routed to a human task rather than silently trusted. The mapping layer is where the residual real-world effort actually sits.
Stage 2

Composing blocks into applications

Stage 1 defined the blocks; Stage 2 is an app builder and the LLM composing them into real applications. Still development, still expert-driven — but the LLM's universe is now the closed, typed set of Stage-1 artifacts, so each app is a bounded assembly of existing blocks, not a project written from scratch. That is where the economics and the safety pay off at once.

An App is a single versioned bundle:

Declarative content
  • an ontology (or a reuse of a shared one)
  • a set of rules, each gated & cited
  • one or more flows (BPMN-lite)
  • connector bindings — which events feed it
  • views — the non-expert screens (queues, forms, a decision-trace timeline)
Runtime posture
  • lives in its own workspace (existing multi-tenant isolation)
  • pins a meta-DSL version; migrates on platform upgrade
  • no unbounded LLM at decision time — only defined Action-actors
  • every run is replayable from the decision graph (agent nodes: audited, not replayed)

Multi-tenancy is not net-new: Context Graph already isolates everything per LIGHTRAG-WORKSPACE — graph, vectors, rules, ontology, decision index. The addressing is three-tier: a Domain is a workspace (its CG, ontology, and L1 block catalog); a Project groups all the apps in that domain; an App is an app-id within the project; runs key under the app-id. Shared blocks are free within a domain; domains isolate through the existing workspace mechanism, untouched. The demo is the degenerate case — one domain, one project, one app. Export/import and a cross-domain marketplace ride on the App-bundle format but are deferred (see decisions).

◆ Two dev stages, then the end-users
Stage 1 (domain architects) and Stage 2 (app builders) are both development — both expert-driven, both LLM-assisted, each constrained by the level above. Together they produce a signed, versioned App. End-users — the people who later operate that App against live events — are a third population entirely, present only at runtime, trusting the App because of how it was made. The platform's job is to make Stage 1 rigorous, Stage 2 safe-and-cheap, and runtime accountable.

That is exactly the essay's claim: let the AI build almost nothing; build the machine that runs what it authored.

Resolved in discussion

Design decisions — walked & resolved

All seven were worked through one at a time. Each callout records the decision, its rationale, and any revisit trigger — the running log of why the platform is shaped the way it is.

✓ 1 · Flow engine — RESOLVED: build lean
Build a lean in-process executor over lifecycle/rules/actions. The flow DSL is ours regardless (it's an L0 Concept, LLM-authored in Stage 1); only the executor was in question. Since the demo is minutes-to-hours human loops — not multi-week processes — a lean executor wins: native decision-trace emission and ontology grounding, no competing BPMN notation, no premature durability machinery. A clean run-store seam is preserved so a durable engine (Temporal-style) can slot in behind it later. Revisit trigger: a target domain with long-running (days/weeks), high-reliability, high-concurrency flows.
✓ 2 · Event bus — RESOLVED: in-process + durable ingress log
In-process asyncio dispatch behind an EventBus interface, with a durable ingress log (append-then-dispatch) so ingress is at-least-once and replayable without a broker. Two things locked now, as they're the interface we can't cheaply change: the event contract {type, payload, source, ts, idempotency_key}, and consumer-side dedupe on idempotency_key (connectors re-deliver — webhook retries, poller overlaps — even in-process). A real broker (Redis Streams / NATS) earns its place only when we need cross-process workers or throughput — out of scope for the demo.
✓ 3 · The mapping boundary — RESOLVED: tiered, unified, demo-deterministic
Mapping tiers by source structure: structured input (webhook JSON, forms) uses a deterministic field-map + Property.coerce (no LLM); the unstructured tail uses LLM extraction validated by ExtractionValidator. Crucially, that LLM-mapper reuses the LLM-agent Action contract (ontology-typed output, confidence, human-fallback, recorded-as-decision) — one mechanism, one audit story, not a second bespoke path. Low-confidence mappings route to a human review task, never silently enter the graph. Every mapped object is stamped with method + confidence + block-version (via rc/provenance), so which inputs crossed a fuzzy boundary is auditable forever. For the demo: deterministic-only at ingress — airtight determinism end-to-end; the LLM tail is designed, not exercised.
✓ 4 · Versioning & migration — RESOLVED: three boundaries, diff-and-approve
Three version boundaries — L0 platform, L1 domain blocks, and run instances — each pins the version of the level above (L2 app pins L1, L1 pins L0). Migration is authoring a delta, not new machinery: an upgrade produces a migration diff that the human approves through the same gate + dry-run + sign-off that authored the originals ("approve the delta, not the whole thing"). In-flight runs pin-to-start and finish on their version — live run-migration is deferred (the demo's short runs make it moot). Ontology changes split by safety: additive → auto, breaking (rename/retype/remove) → a reviewed old→new mapping. Every object records the block-version that produced it, so past decisions stay interpretable under the rules that made them.
✓ 5 · Human-in-the-loop — RESOLVED: sign everything, graduated by risk
All L1 blocks and the L2 app composition require sign-off — a signed App can't rest on unsigned foundations — but scrutiny graduates by risk: agent-actions & egress webhooks (non-reproducible / real side effects) get the hardest look; the app composition gets the lightest (everything it wires is already signed). Re-approval triggers only on behaviour-affecting diffs, detected by re-running the artifact's own dry-runs / flow test-cases — cosmetic edits are lightweight/auto. This shares one mechanism with #4: migration and re-approval are both "approve the diff." Every approval is recorded natively as a decision (who / why / when).
✓ 6 · Packaging & namespaces — RESOLVED: Domain / Project / App
Three-tier addressing inside the existing isolation: Domain = workspace (holds CG + ontology + the L1 block catalog); Project = the grouping of all apps in a domain (the solution/portfolio); App = app-id within the project (an L2 composition: flows / rules / connectors / views); runs key under app-id. Shared blocks are free within a domain; domains isolate via the existing LIGHTRAG-WORKSPACE mechanism, untouched. The demo is the degenerate case — one domain / one project / one app. The App bundle (a portable, versioned JSON of catalog refs + composition + pinned versions) is designed now — it's the same serialization #4/#5 operate on; export/import polish and a cross-domain marketplace are deferred.
✓ 7 · Studio UX — RESOLVED: conversational drafts a diff
The recurring gesture across #4/#5/migration is "review a diff to a typed, versioned artifact" — so the Studio is built on it. Conversational is the input method, not the state: you talk to the LLM to draft or change something, and it proposes a diff to a structured source-of-truth view (ontology graph, rule list + dry-run, flow canvas) that you edit / accept / reject; the artifact versions. "Reversible" = versioned artifacts with history + revert. Reuse: extend the existing Ontology and Rules UIs; a light Studio shell adds Domain/Project/App navigation + history; the flow canvas (BPMN-lite editor) is the one genuinely net-new surface for now. Future: richer visual diagram representations for both flows and states.
If we build it

A build path — thin vertical slices

Each phase is a demonstrable end-to-end slice, not a horizontal layer. The goal is to prove the loop early and thicken it.

  1. The loop, minimal. Event contract + in-process bus + one inbound-webhook connector → a single rule evaluation → a decision trace written to the graph. No flows yet. Proves events-in → deterministic-decision-out.
  2. Flow engine MVP. Linear-plus-one-gateway flows: event → task(action) → gateway(rule) → state transition, with a persisted run log and a replay view. Composes lifecycle + rules + actions under an orchestrator.
  3. Stage-1 Studio. The reversible authoring surface over OntologyAuthor/RuleAuthor plus the new flow canvas; sign-off freezes an App. Extends existing UIs where possible.
  4. Stage-2 packaging. App = versioned bundle in a workspace; instantiate, run against live events, show the non-expert queue + decision-trace timeline. Add meta-DSL version pinning.
  5. Thicken. The agent action handler (LLM-as-actor with a typed contract + confidence routing), timers/scheduler, parallel gateways, connector breadth (poller, email/Slack), LLM-assisted mapping, migration tooling, and richer visual diagrams for flows & states.
◆ The demo that proves the thesis
A non-expert watches a request arrive from a webhook, get mapped to ontology terms, hit a rule-driven gateway, route to a human sign-off, and land in a terminal state — then opens the decision trace and sees who/why/when for every hop, with no LLM anywhere in that path. That single screen is the argument.
